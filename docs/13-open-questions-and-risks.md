# 13 — Open Questions and Risks

Each item is something the docs don't fully settle. **Resolve all of them in the B0 sandbox spike** ([12](./12-implementation-plan.md#b0--sandbox-spike-scripts-only-can-run-in-parallel-with-track-u)) and update this file with findings.

## Spike results (2026-09-28)

Webhooks (R9) were not retested. Everything else below was called against the sandbox.

The backend can start. Two card-rail constraints are not feasible on this account until Airwallex changes the platform configuration:

1. **Funds splits cannot go to individual connected accounts on model 2.2.** Create returns `Individual account funds split is only supported for the model 2.1`. Airwallex confirmed this sandbox is **2.2** (seller is Merchant of Record; split destination must be a business). **2.1** (platform is Merchant of Record) can split to an individual seller. Decision for this demo: every user account and the service-fee account are `BUSINESS` ([03 §2](./03-airwallex-integration.md#gateway-models-21-and-22), [08](./08-seeding.md)). To support genuine individual freelancers later, ask Airwallex to enable 2.1 instead of pretending fixture companies are individuals.
2. **Funds Split Reversal does not work before the destination has the money.** Reversal of a `CREATED` split and of a `RELEASED` but not `SETTLED` split both returned `Insufficient funds in USD currency` while the destination available balance was `0`. A partial Refund on the PaymentIntent succeeded anyway, and the `CREATED` split stayed `CREATED`.

`connected_account_id` on PaymentIntent create is also rejected (`not enabled for payment acceptance`) for both the individual seller and the business account. A PaymentIntent with no `connected_account_id` can be paid and then split to the business account, so that field is not required for the hold-and-release test. Platform `payments_visa` and `payments_mastercard` are still `PENDING`. Native card confirm is disabled; Drop-in and the Hosted Payment Page work.

**Cancelling an unpaid PaymentIntent (checked 2026-10-07).** Create returned `REQUIRES_PAYMENT_METHOD`. `POST /pa/payment_intents/{id}/cancel` returned `CANCELLED`, and a later retrieve stayed `CANCELLED`, so the intent is no longer payable. A follow-up `confirm` with the test card was rejected (`400 validation_error`, native API access disabled). That same confirm error happens on a payable intent (R12), so it does not add evidence beyond the `CANCELLED` status. Checkout cancel still refunds a capture that wins the race.

## Decisions already made (and why)

| Decision | Reason |
| --- | --- |
| Buyer funds the **whole offer up front**, not per milestone | One checkout in the demo; showcases held splits and delayed release clearly. |
| Card payment is created on the **platform** for now | This sandbox is model 2.2, whose intended create sets `connected_account_id`. That field is rejected until the seller is enabled for payment acceptance, so the working create omits it and still splits to a business account. Model 2.1 (`platform_mor`, individual destinations) is the later path for real freelancers. |
| Fee **deducted from seller**, split to a seeded **Revenue CA** plus a small platform reserve | Makes "funds split to a known account" visible while keeping the platform's net positive. The Revenue CA is a business account created by seed, with no login. |
| Every connected account is **`BUSINESS`** | This sandbox is gateway model 2.2, which rejects Funds Splits to individual accounts. Model 2.1 would allow individual sellers. The product UI still treats users as freelancers. |
| **Card rail default**, wallet rail secondary | Brief centres on payment acceptance + Funds Split; wallet rail shows CA money movement and enables server-side seeding. |
| **Embedded milestones** in offers | Atomic updates, simple reads, small arrays. |
| **No Redis** | No requirement that Mongo plus deterministic request IDs can't meet. |
| **Links-only deliverables** | Per brief; avoids file storage. |
