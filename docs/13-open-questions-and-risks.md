# 13 — Open Questions and Risks

Each item is something the docs don't fully settle. **Resolve all of them in the Phase 0 spike** ([12](./12-implementation-plan.md#phase-0--sandbox-spike-scripts-only-no-ui)) and update this file with findings.

| ID | Question / risk | Impact if wrong | Mitigation / fallback |
| --- | --- | --- | --- |
| **R1** | **Platform capabilities.** Connected accounts, the "collect directly" gateway model, and Funds Split all need enabling on the sandbox account by Airwallex. The quickstart says to contact your Account Manager. | Blocks everything except basic payments. | Request early (setup step 2). While waiting, build Phases 1 and 3 (no Airwallex dependency). |
| **R2** | **Minimal connected-account payload.** What `individual_details` fields does `submit` require in sandbox for our chosen country? Can `simulation/update_status` with `force: true` skip missing fields? | Provisioning fails. | Spike 02 iterates on the payload; store it as `identity-fixture.ts`. Pick one country (for example AU, US, or GB) and use it for all users. |
| **R3** | **Held splits in sandbox.** Does a split created with `auto_release: false` stay in `CREATED` until released, given back-to-back T+0 settlement? The API says splits must be created "before funds settlement". | Delayed release (the core of the brief) doesn't work on the card rail. | Create splits immediately on success (already planned). If holds still fail: **Fallback A:** keep the card rail for payment acceptance, and model escrow as funds retained on the platform (no split at payment time). On approval, do a CA Transfer to the seller. Funds Split is then shown on a separate "instant split" example (for example the platform fee with `auto_release: true`). **Fallback B:** ask Airwallex to configure a settlement delay on the sandbox account. |
| **R4** | **Maximum hold duration** for unreleased splits (days? until a settlement cutoff?). | Long-running contracts might auto-release or fail. | Ask Airwallex. For a demo, contracts are completed within minutes, so this is low impact. Document the limit. |
| **R5** | **Charges authorization.** The CA Transfers doc mentions debiting a CA "subject to authorization from the connected account". Do Charges against sandbox CAs need a consent/config step? Does `source` accept `acct_...` IDs (older examples show numeric IDs)? | Wallet rail (and seeded active contracts) don't work. | Spike 04. If Charges are blocked, seed active contracts via the card rail using the **Hosted Payment Page** plus a manual browser step, or ship with fewer seeded active contracts. |
| **R6** | **Balance endpoints on behalf of CAs.** Confirm `balances/current` and `balances/history` work with `x-on-behalf-of` for our CA tier, and which transaction types show up for splits (`SPLIT`?) and CA transfers. | Wallet page empty or confusing. | Map types after observing real data. Fall back to our own ledger (`activity`) for history. |
| **R7** | **Reversing unreleased splits.** Is a Funds Split Reversal required (or allowed) before refunding a milestone whose splits are still `CREATED`? Can we refund without reversing, and do unreleased splits then fail or remain dangling? | Refund fails, or seller later receives funds for a refunded milestone. | Spike 07 tries both orders. Worst case: reverse after release is supported (docs say reversals take money back from a CA), so release then reverse then refund works, though it's ugly and should be hidden from the user. |
| **R8** | **API versioning.** Which version does the sandbox account default to? Is there an `x-api-version` header to pin it? Newer versions change some statuses (for example `CLOSED`/`DORMANT` accounts from `2026-08-21`). | Payload shape drift. | Pin the version in the client once confirmed; record it in `.env.example`. |
| **R9** | **Webhook payload shapes** differ slightly by product (`account_id` vs `accountId`, `data.object` vs `data`). Which events are available to subscribe in the sandbox web app (for example funds split reversal events)? | Handlers can't find objects. | Normalizer + logging of raw payloads in the spike; sync fallback covers gaps. |
| **R10** | **Processing fee netting.** With splits totalling 98% of the payment, does the platform's 2% remainder cover Airwallex's sandbox processing fee? Are fees charged in sandbox at all? | Split creation fails for exceeding available amount. | Make `PROCESSING_RESERVE_PERCENT` configurable (already planned). Observe the actual fee in balance history. |
| **R11** | **Funds Split destination eligibility.** Destinations must "pass KYC". Does a force-activated sandbox CA qualify? Does a split to a CA other than the PI's `connected_account_id` (the Revenue CA) work? The docs' multi-seller example suggests yes. | Revenue split fails. | If not allowed, leave the fee on the platform account (no revenue split) and show the fee as "retained by platform" on `/platform`. |
| **R12** | **Drop-in availability** on a fresh sandbox (the sandbox settings list Hosted Payment Page as the default checkout type). | Checkout UI changes. | Use `redirectToCheckout` (HPP) with `successUrl` = return page. The rest of the flow is unchanged. |
| **R13** | **Shared guest accounts.** Concurrent visitors acting on the same seed account. | Confusing demo; state races. | Conditional updates; large guest pool; round-robin assignment instead of random; periodic reset. |
| **R14** | **Sandbox transaction limits** (maximum transaction amount of about 10,000 local currency, monthly volume of about 500,000). | Big offers or heavy demo use fail. | Cap offer totals at $9,000 in validation; reset/seed sparingly. |

## Decisions already made (and why)

| Decision | Reason |
| --- | --- |
| Buyer funds the **whole offer up front**, not per milestone | One checkout in the demo; showcases held splits and delayed release clearly. |
| **Collect payments directly** (platform is MoR) | Marketplace pattern; sellers don't need payment-acceptance capability. |
| Fee **deducted from seller**, split to a seeded **Revenue CA** plus a small platform reserve | Makes "funds split to a known account" visible while keeping the platform's net positive. |
| **Card rail default**, wallet rail secondary | Brief centres on payment acceptance + Funds Split; wallet rail shows CA money movement and enables server-side seeding. |
| **Embedded milestones** in offers | Atomic updates, simple reads, small arrays. |
| **No Redis** | No requirement that Mongo plus deterministic request IDs can't meet. |
| **Links-only deliverables** | Per brief; avoids file storage. |
